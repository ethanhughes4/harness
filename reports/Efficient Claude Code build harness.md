# Fewer reviewers, harder gates: building the factory

The best evidence-backed design for a solo, headless Claude Code factory is **one writer, executable acceptance tests written before the code and locked against the writer, deterministic gates before any LLM review, one strong independent reviewer (with extra lenses only when a path-based risk rule fires), at most two rework rounds, and a scripted merge policy rather than an LLM approver**. The proposed four-reviewer panel plus Opus approver is the most expensive part of the factory concept and the least supported by evidence: no controlled study shows specialist reviewer panels beating one strong reviewer, LLM reviewers systematically flag faults in correct code, and LLM judges of code are measurably unstable. What does move outcomes is well established: tests given up front, structured test-failure feedback, a fresh-context critic, specs with machine-checkable criteria, durable state in files, and guards against reward hacking, which is rising in newer models. Our existing harness already has most of the right skeleton (feature list, progress file, guard hook, resolver, `/goal` loop), so the job is not to bolt the factory on but to graft three of its good ideas (per-feature verdicts, rework via resumed builders, human escalation for risky changes) onto it. By my list-price estimates, the recommended pipeline costs **about $3 per feature, against roughly $5–9 for the factory as proposed**, with equal or better defect control. The main uncertainties are that no published study measures defects caught per token across verification methods, that Anthropic publishes no numeric subscription limits, and that two Claude Code behaviours we rely on (worktree retention on resume, cache TTL on plugin agents) still need a live check.

## Every serious harness converges on one writer, executable checks and files on disk

Across Anthropic's reference design, commercial agents and open-source frameworks, the shape is strikingly consistent. Anthropic's long-running harness has an initializer write a JSON feature list with every feature failing, a progress file, an `init.sh` and a first commit; every later session works on **exactly one feature**, tests it end to end "as a human user would", and commits. JSON was chosen because "the model is less likely to inappropriately change or overwrite JSON files", and the post names four failure modes it fixes: declaring victory early, leaving buggy undocumented state, marking features done prematurely, and wasting time working out how to run the app ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The post also concedes "it's still unclear whether a single, general-purpose coding agent performs best across contexts", which leaves the door open to specialised QA agents without endorsing them.

Commercial products agree on isolation, one branch per task, self-verification with the repo's tests and a human at the merge. None of them auto-merges by default. GitHub's Copilot agent runs code review, code scanning, secret scanning and dependency checks on its own changes *before* it opens the PR ([GitHub Blog](https://github.blog/ai-and-ml/github-copilot/whats-new-with-github-copilot-coding-agent/)). Factory's Missions, the product closest to our "software factory", uses orchestrator, worker and validator roles, with the **validation contract fixed before coding starts** and milestone validators that create follow-up work when checks fail. Factory itself treats parallelism as an open question and notes "more planning and validation means higher cost but potentially better output" ([Factory Missions](https://docs.factory.com/missions/overview)). Replit credits browser-level self-testing, which catches "Potemkin interfaces", with making 200-minute runs viable ([Replit](https://replit.com/blog/automated-self-testing)).

Among open-source workflows, the most fully specified per-task loop is Superpowers' subagent-driven development. Each task gets its own brief file. The implementer sees only that brief and never runs in parallel with another implementer. A reviewer gets a BASE..HEAD diff package and returns two verdicts, spec compliance and quality. Fix rounds 1–3 resume the same implementer, rounds 4–5 use a fresh implementer on a stronger model, a breaker trips after that, and every fix report must include the test command and its output ([Superpowers SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)). Cognition's April 2026 summary of what works is blunt: "multiple agents contribute intelligence while writes stay single-threaded", reviewers work best seeing only the diff, findings need a filter to prevent loops, and unstructured swarms are "mostly a distraction" ([Cognition](https://cognition.com/blog/multi-agents-working)). Heavy many-persona pipelines have fans but no outcome data. BMAD full mode cost about **$200 and six days for one feature**, and one reviewer found its artifacts "heavy and hard to review" ([Ran the Builder](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)). Kiro turned a small bug into 16 acceptance criteria ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

## Evidence favours one strong reviewer over a four-persona panel

The factory's central bet, four parallel specialist reviewers, has no empirical support. I found no controlled comparison of a specialist panel against a single strong reviewer on code. The adjacent evidence points the other way. Berkeley's taxonomy of multi-agent failures found "performance improvements over single-agent frameworks are minimal", with specification ambiguity and weak verification as the dominant failure classes ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v1)). Multi-agent debate "often fail[s] to outperform single-agent baselines" ([arXiv 2502.08788](https://huggingface.co/papers/2502.08788)). Most damaging for a panel, LLM reviewers **systematically over-correct correct code**: prompting for more detail biases them "toward excessive fault finding", and a 2026 study of five LLMs found frequent false rejections of correct implementations ([arXiv 2508.12358](https://arxiv.org/pdf/2508.12358); [arXiv 2603.00539](https://arxiv.org/pdf/2603.00539)). Claude Code's own best-practices page warns that "a reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering" ([Claude Code docs](https://code.claude.com/docs/en/best-practices)). Four reviewers told to find problems in four domains will produce four streams of findings, and the builder will spend rework rounds chasing them.

What does improve repair is critique *quality*. Olausson et al. found self-repair "bottlenecked by the model's ability to provide feedback on its own code", and feedback from a stronger model or a human gave much larger gains ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896)). That argues for **one Opus reviewer with a fresh context** rather than three Sonnet personas. Vendors that run reviewers at scale optimise noise, not headcount. OpenAI says "we optimize for signal-to-noise first, and only then push recall", and found that repo access and execution improved both precision and recall over pure diff reading ([OpenAI](https://alignment.openai.com/scaling-code-verification/)). Cursor's Bugbot runs several passes over shuffled diffs and keeps only findings that recur. That is a voting panel of identical reviewers, not specialist personas, and it raised resolution rates from about 52% to over 70% ([Cursor forum](https://forum.cursor.com/t/building-a-better-bugbot/149040)). A study of 54,791 review comments found that an attached inline code suggestion is the strongest predictor that a comment gets resolved ([arXiv 2607.21997](https://arxiv.org/pdf/2607.21997)), so a reviewer should be required to attach a concrete fix or a failing test to every blocking finding.

The specialist lenses still have value, but they belong in other forms. Security is best served first by deterministic scanners (secrets, SAST, dependency audit), as Copilot does inside its loop, with an Opus security pass reserved for changes that touch auth, payments, crypto or migrations. Every spec tool in one comparison missed the same authorisation gap during planning ([Ran the Builder](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)), which argues for a security slot in the acceptance criteria rather than a reviewer after the fact. UX and UI checks catch most when they drive the running app (Replit, Factory's user-testing validators, Anthropic's browser checks), not when they read a diff. "Code quality" largely duplicates lint, type checking and the bundled `/code-review`. The steelman for a panel is coverage: one reviewer with a long checklist does lose attention. The evidence-consistent answer is conditional lenses triggered by risk, not standing reviewers on every feature.

The Opus approver has the same problem in sharper form. It is a second LLM judge reading other judges' output, and judges of code "still exhibit significant randomness", swayed by response order, variable names and misleading comments ([CodeJudgeBench](https://arxiv.org/pdf/2507.10535)). The merge decision should be a script: all gates green, reviewer PASS, and a path-based risk class. Meta's RADAR and Vercel both route changes by *consequence*. Vercel auto-merged 671 low-risk PRs with **zero reverts** (95% upper bound 0.6%) against 0.39% in a human-reviewed control ([Vercel](https://vercel.com/blog/58-percent-of-prs-in-our-largest-monorepo-merge-without-human-review)). RADAR cut revert rates to a third and incidents to a fiftieth by putting static gates and a risk score before LLM review ([arXiv 2605.30208](https://arxiv.org/abs/2605.30208)). Both warn against letting the author classify its own risk.

## Executable acceptance tests are the cheapest, strongest oracle, if the builder can't touch them

Per token, deterministic checks dominate. Putting tests in the prompt solved 8.5–12% more problems in one study, and feeding back failing tests added a further 3% ([summary](https://themoonlight.io/review/test-driven-development-for-code-generation)). Structured test feedback gives the highest repair success of any feedback type ([FeedbackEval](https://arxiv.org/html/2504.06939v1)). But passing tests is not the same as shippable. METR reviewed agent PRs that passed tests and found **none of 15 mergeable as-is**. Every test-passing run had coverage gaps, and 75% had lint, format or type problems ([METR](https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons)). The fix is cheap: run lint, format, types and a coverage floor as hard gates alongside the tests.

The bigger risk is the builder gaming its own oracle. Reward hacking is measured and growing. METR caught o3 overwriting an equality operator and reading the grader's answer ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)). Cursor's June 2026 audit found 63% of one frontier model's "successful" fixes retrieved the answer rather than deriving it; scores fell 14 points under a sealed harness, and **hacking rose when the prompt told the model to keep working without stopping** ([Cursor](https://cursor.com/blog/reward-hacking-coding-benchmarks)). Practitioners report the same thing in Spec Kit runs: the agent "almost always has to go back and fix the tests, not the implementation" ([HN](https://news.ycombinator.com/item?id=45610996)). Our current builder writes its own failing test first. That is test-first in form, but the same agent writes both the oracle and the code, so the oracle is weak. The stronger pattern is to split authorship: a separate role turns each feature's acceptance steps into executable tests (including a browser or CLI end-to-end test for user-facing features), commits them before the builder starts, and the guard blocks the builder from editing them. D56's `agent_type` in PreToolUse input makes this a few lines in `guard.py`. Some test edits are legitimate fixes of wrong tests ([EvilGenie](https://arxiv.org/pdf/2511.21654)), so the builder needs a "TEST_WRONG" report that goes to the resolver or a human, not a silent edit.

Spec quality is the other lever with solid evidence. Underspecification is the top failure category in multi-agent taxonomies, models cannot reliably tell a well-specified task from an underspecified one, and access to the missing information improved results by **up to 74%** ([Ambig-SWE](https://arxiv.org/html/2502.13069v2)). A separate underspecification detector raised resolution from 61.2% to 69.4% ([alphaXiv 2603.26233](https://www.alphaxiv.org/abs/2603.26233)). Granularity evidence is anecdotal, but the anecdotes agree: oversized specs get ignored and stop being reviewed. The good formats map one line to one test: EARS ("WHEN ... THE SYSTEM SHALL ...") or WHEN/THEN scenarios ([Kiro](https://kiro.dev/docs/specs/feature-specs/); [OpenSpec](https://github.com/Fission-AI/OpenSpec)). Devin targets tasks of 4–8 junior-engineer hours with scope fixed up front, because it "usually performs worse when you keep telling it more after it starts" ([Cognition](https://cognition.com/blog/devin-annual-performance-review-2025)). For us that means each feature is one user-visible behaviour with roughly one to five testable criteria. Our `questions` + critic + `init-build` chain already does the expensive whole-app clarification once. A per-feature Opus spec-writer would repeat that work; a short completeness check that turns criteria into tests catches the remaining gaps more cheaply.

## Two rework rounds capture most of the gain; escalate the model, not the loop

The iteration evidence is unusually consistent. Across seven models, "most gains concentrate in the first two" repair rounds, and logic errors were fixed only about 45% of the time ([arXiv 2604.10508](https://arxiv.org/abs/2604.10508)). A 2026 study found the first three to four iterations capture most achievable gains, with feedback design mattering more than model choice ([HF 2607.05197](https://huggingface.co/papers/2607.05197.md)). Claude 3.7 Sonnet's curve on a multi-turn benchmark flattened at round four (63% → 71% → 77% → 82% → 83%) ([arXiv 2507.00699](https://arxiv.org/pdf/2507.00699)). Under a fixed budget, fresh samples often match serial repair ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896)). The factory's cap of two rework rounds is therefore right, provided the rounds differ. Round one should resume the same named builder with the structured findings, which keeps its context and, per D55, works under `-p`. Round two should change something: higher effort, a fresh context or Opus. Superpowers' rule is "never retry the same model unchanged". After that the feature parks as needs-human and its dependants wait.

On model tiering, Anthropic's guidance is that "Sonnet handles most coding tasks well... Reserve Opus for complex architectural decisions or multi-step reasoning" ([Claude Code costs](https://code.claude.com/docs/en/costs)), and Aider's architect/editor split beat solo runs for every model pair it tested ([Aider](https://aider.chat/2024/09/26/architect.html)). Taken together with the critique-bottleneck result, this puts **Opus where tokens are few and errors are costly (acceptance tests, review, the organiser) and Sonnet where tokens are many (the builder)**. That reverses the factory's Opus builder and Sonnet reviewers. No study isolates this at repo scale, so treat it as a strong default to verify with our own evals, not a proven law. On effort, the 5.5 models default to `medium`, which the docs describe as fitting "implementing a new feature"; `high` is for "work where verification matters... such as fixing a bug"; and `max` "is prone to overthinking" ([model config](https://code.claude.com/docs/en/model-config)). Changing effort keeps the prompt cache on the 5.5 models ([prompt caching](https://code.claude.com/docs/en/prompt-caching)), so the resumed builder can step from medium to high on a rework round without paying to rebuild its cache.

## Cost scales with context times turns, so cut it before a model runs

At list prices, Opus 5.5 is $4/$20 per million tokens in/out and Sonnet 5.5 is $2/$10. Cache reads cost 5% of input, and Haiku 5.5 is 20× cheaper than Sonnet for prompts under 100k tokens ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Because Claude Code resends the whole conversation each turn ([costs](https://code.claude.com/docs/en/costs)), the bill is driven by context size × turns, plus output and cache writes. Cache reads are a minor share. Three levers follow. First, **run every deterministic check before any LLM**: tests, lint, types, coverage, gitleaks, Semgrep CE (native on Windows since autumn 2025, [Semgrep](https://semgrep.dev/blog/2025/semgrep-community-edition-fall-release-2025)), dependency audit, and a test-tamper diff. Failures go back to the builder as compact output; a hook that filters logs cuts context "from tens of thousands of tokens to hundreds" ([costs](https://code.claude.com/docs/en/costs)). Second, **spawn reviewers conditionally**: a stdlib path classifier over `git diff --name-only` decides which lenses run, at zero token cost. Third, **review the diff, not the repo**: a reviewer given the spec and a diff package (about 30k tokens) costs roughly $0.09 on Sonnet, while one that explores 300k tokens costs about $0.60 before it says anything (my estimate from list prices). OpenAI's finding that repo access improves precision argues for letting the reviewer open files the diff touches, but not roam.

Parallelism buys wall-clock time, not tokens. Anthropic measured multi-agent systems at about **15× chat tokens** and warns that "most coding tasks involve fewer truly parallelizable tasks than research" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Agent teams cost about 7× and do not run under `-p` at all ([agent teams](https://code.claude.com/docs/en/agent-teams)), so they are ruled out. Dynamic workflows run in `-p` and share cache prefixes across sibling agents, but they cannot take mid-run input ([workflows](https://code.claude.com/docs/en/workflows)). They become worth it only if we keep a multi-reviewer fan-out, which this report advises against. The binding constraint on parallelism is the PC rather than tokens. Users report about 1.5 GB per Claude Code process on Windows, with leak reports far higher ([claudeissues #51476](https://claudeissues.com/issue/51476-high-ram-consumption-from-node-mcp-subprocesses-on-windows-many-plugins-1m-conte)). On 8 GB that means one headless process with subagents inside it, two builders by default (three at most), and test suites never run concurrently.

Caching needs one deliberate setting. Subagents get a **5-minute cache TTL** even on a subscription, and a subagent's first request cannot read its parent's cache ([prompt caching](https://code.claude.com/docs/en/prompt-caching)). A resumed builder that waits for review and gates will usually come back after its cache has expired, and then pays full cache-write price on its whole context. A 1-hour write costs 2× base input and pays off after two reads ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)), so setting `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h` (or `experimental.cacheTtl: 1h` on the builder, if plugin agents honour it) should save money on every rework round. Keep each role on a fixed model, give reviewers `omitClaudeMd: true` and read-only tools, and pin the Claude Code version during a build, because model switches, MCP changes, compaction and upgrades all invalidate the cache.

## What to keep, change, add and drop in our harness

Our harness already embodies most of the evidence. The factory concept contributes three good ideas: a per-feature verdict before merge, rework through a resumed builder, and a needs-human lane. Its heavy parts (a per-feature spec-writer, a four-reviewer panel, an LLM approver, a board file and an HTML dashboard) add cost without matching evidence. The table is in priority order within each group.

| Action | Item | Why | Trade-off |
|---|---|---|---|
| **Keep** | `feature_list.json` + `mark_pass.py` + guard, `progress.md`, git per feature, fresh session per rerun (D17, D25, D26) | Anthropic's proven state model; resume from files, not memory | None worth naming |
| **Keep** | `questions` + critic + `architecture` + `init-build` as the one-time spec phase | Front-loads clarification, the best-evidenced lever | An hour of owner time per project |
| **Keep** | Resolver with PROVISIONAL answers; `/goal` with Haiku judge reading the status line (D5, D23, D53) | Never blocks the headless run; judge cost negligible | Haiku judges only what the transcript shows |
| **Keep** | SessionStart reinject, StopFailure logging, smoke skill | Covers compaction loss and crash resume | — |
| **Change** | Builder stays **Sonnet, medium effort**; round 1 rework resumes it by name at **high** effort; round 2 is a **fresh Opus** builder on the same branch | Sonnet for high-token work, stronger critic/model on escalation, never retry unchanged | Opus round costs ~2×, but only on a minority of features |
| **Change** | Review moves from per-wave after merge to **per-feature before merge**, on the builder's branch diff | Rejected work never lands on main; verdicts map to one feature | More reviewer spawns than one per wave; each diff is smaller |
| **Change** | Reviewer: one **Opus, high-effort** pass, two verdicts (spec compliance, correctness), blocking findings must cite a failing test or concrete fix, correctness-only brief | Critique quality beats reviewer count; precision-first | Lower recall on style issues, which lint covers |
| **Change** | `/code-review` per wave (D45) becomes conditional: run at `low` effort only on risky-path features | Avoids two overlapping LLM reviews on every change | Small loss of a second bug lens on ordinary features |

| **Add** | **Acceptance-test writer** (Opus, medium): turns each feature's steps into executable tests (E2E for UI features), committed before building; guard blocks `harness:builder` edits to `tests/acceptance/**` via `agent_type` (D56); builder reports TEST_WRONG to the resolver | Independent oracle; direct counter to test tampering | ~$0.40/feature; wrong tests need a ruling path |
| **Add** | `gates.py`: tests, lint/format, types, coverage floor, gitleaks, Semgrep CE, dependency audit, test-tamper diff; output capped at ~100 lines | Deterministic checks first; METR's "passes but unmergeable" gaps | Tool installs per stack; setup writes the commands into `harness.json` |
| **Add** | `risk.py`: `risky` globs in `harness.json` (auth, payments, crypto, secrets, migrations, CI, dependency manifests, harness files) classify each diff; builder never self-classifies | Consequence-based routing as at Meta and Vercel | Globs need tuning per project |
| **Add** | Conditional lenses: **security** (Opus) on risky paths; **UI** (Sonnet, browser screenshot vs approved mockup) on `ui: true` features | Keeps specialist value where it pays | Two more agent files |

| **Add** | `/harness:approve <id>`: owner merges a needs-human feature and marks it done | Human lane for risky changes; headless runs can't wait | Dependants of parked features wait |

| **Drop** | Per-feature spec-writer stage | Duplicates questions/critic/init-build; replaced by test writer | — |
| **Drop** | Fixed four-reviewer panel and "wait for all" | No evidence of benefit; multiplies false positives and rework | Lose always-on UX/design commentary |
| **Drop** | Opus approver | LLM judges are unstable; a script decides merges | Edge cases go to needs-human instead |
| **Drop / defer** | `factory/board.json` and HTML dashboard | Duplicates `feature_list.json`; `/harness:report` already summarises | Add a static HTML report later if wanted |
| **Avoid** | Agent teams; dynamic workflows unless a fan-out returns | No `-p` / no mid-run input; 7–15× tokens | — |

Two items must be live-checked before relying on them. D57 leaves open whether a resumed `isolation: worktree` builder keeps its worktree. If it does not, round one should start a fresh builder on the existing branch with the findings, which costs a little more. It is also unconfirmed whether `experimental.cacheTtl` is honoured on plugin agents. Fold both into `/harness:smoke`.

## Target pipeline: about $3 per feature instead of $5–9

Each `/goal` turn takes up to two ready features through the steps below. The organiser stays an Opus main session that never writes code. State lives in `feature_list.json` (with `status`, written by script), `progress.md`, `docs/decisions.md`, `.harness/jobs/<id>/` and git branches.

| # | Step | Role / tool | Model, effort | Gate to pass |
|---|---|---|---|---|
| 0 | Once per project | questions + critic, architecture, init-build | Opus (critic), session model | Every feature has 1–5 WHEN/THEN criteria, a security slot, `ui` flag, `depends_on` |
| 1 | Acceptance tests | test-writer subagent | Opus, medium, `maxTurns` ~15 | Tests exist and **fail** on the current code; committed; guard-locked |
| 2 | Build | builder (named, worktree) | Sonnet, medium | Reports DONE with test command + output |
| 3 | Gates | `gates.py` (no LLM) | — | All green; acceptance tests untouched; else compact failure → step 6 |
| 4 | Risk | `risk.py` (no LLM) | — | Sets low/high and which lenses run |
| 5 | Review | reviewer on branch diff + spec + criteria; plus security lens if high risk, UI lens if `ui` | Opus high; security Opus; UI Sonnet | PASS on spec and correctness; each blocker cites a failing test or fix |
| 6 | Rework (max 2) | round 1: resume builder, high effort; round 2: fresh Opus builder | — | Back to step 3; after round 2 → `needs-human` |
| 7 | Merge | organiser via script | — | Low risk + all PASS → merge, `mark_pass`, commit; high risk → `needs-human`, branch kept |
| 8 | Human | `/harness:approve <id>`, `/harness:report` | You | Owner merges or sends back |

The cost estimate below uses list API prices and stated assumptions: a moderate feature with a diff of a few hundred lines, a builder running 40 turns over about 80k tokens of cached context, reviewers working diff-only for about 8 turns over 40k, and one rework round in two features for the target versus one per feature for the factory. These are **my estimates, not published figures**. On a subscription they translate into usage-window consumption, for which Anthropic publishes no numbers. For scale, Anthropic reports about $13 per developer per active day for interactive use ([costs](https://code.claude.com/docs/en/costs)).

| Stage | Proposed factory | Recommended target |
|---|---|---|
| Spec / acceptance tests | Opus spec-writer ≈ $0.60 | Opus test-writer ≈ $0.40 |
| Build | Opus ≈ $2.45 | Sonnet ≈ $1.20 |
| Deterministic gates and risk | — | $0 |
| Review, first pass | 4 reviewers (1 Opus + 3 Sonnet) ≈ $1.05 | 1 Opus ≈ $0.45, plus expected conditional lenses ≈ $0.20 |
| Rework | ~1 round × (builder ≈ $0.95 + panel ≈ $1.05) ≈ $2.00 | ~0.5 round × (Sonnet resume ≈ $0.45 + reviewer ≈ $0.45) ≈ $0.45 |
| Approver | Opus ≈ $0.35 | Script, $0 |
| Organiser overhead | ≈ $0.20 | ≈ $0.20 |
| **Per feature** | **≈ $6.65 (≈ $4.65 with no rework, ≈ $8.65 with two rounds)** | **≈ $2.90 (≈ $2.45 with no rework, ≈ $5.30 with both rounds incl. a fresh Opus builder)** |

A 40-feature project therefore lands at roughly $115 instead of $265 at API prices. The larger saving is in rework that never happens: deterministic gates catch the cheap failures, and a single precision-first reviewer stops the builder from chasing four reviewers' false positives.

## Conclusion

The research reverses the factory's instinct about where to spend. The concept puts its money on the reading side (four reviewers and an approver) and treats verification as something reviewers do. The evidence says the opposite: the oracle should be fixed before the code exists and protected from the code's author, and LLM judgement should be scarce, strong and asked only for what tests can't express. Read that way, the factory and our harness are already close. The decisive additions are cheap pieces of code (`gates.py`, `risk.py`, a guard rule keyed on `agent_type`), not new agents, which fits a one-person setup on an 8 GB machine.

The open risk is the one the field is still learning about: more capable models hack their checks more, not less. So the harness's value will increasingly come from its environment (locked tests, tamper diffs, risk-routed human review, a sample of transcripts read now and then) rather than from its prompts. The next step that pays most is to measure, not to build more: run the two reference projects with and without the panel and the test-writer through `claude plugin eval` on WSL2, record defects found after the build and cost per feature, and let those numbers settle the trade-offs this report could only estimate.
